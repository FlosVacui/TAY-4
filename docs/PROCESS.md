# Как ведётся разработка ТАУ-3 NG

Этот документ задаёт правила работы. Их обязаны соблюдать каждая сессия и каждый субагент. Если правило мешает делу, его сначала меняют здесь и записывают в [журнал](history/JOURNAL.md), а уже потом работают по-новому.

**Термины этого документа:**
- **график работ** — Excel-файл `tracker/ТАУ-3_NG_график.xlsx`;
- **диаграмма** — график функции в программе;
- **«Паритет»** — лист графика работ, где каждой функции и поведению 1.1 и CONTROL 2 сопоставлено состояние в новой программе.

**Пути** внутри репозитория пишутся через `/` (`docs/…`), вне его — через `\` (`..\CONTROL_src`).

## Роли
Этот раздел — источник правды о ролях. Раздел `roles` в `tracker.yaml` (лист «Легенда») — его копия, её сверяют на воротах каждого этапа.

Модель и effort субагента назначает оркестратор, всегда явно (решение пользователя от 02.11.2026). Журнал, график работ и граф обновляют скрипты оркестратора, а не отдельные агенты.

| Роль | Модель / effort | Что делает |
|---|---|---|
| Оркестратор, архитектор | Opus 5.5, основная сессия | Решения, ADR, задания субагентам, приёмка, коммиты, учёт, граф |
| Аналитик требований | Sonnet 5.5 / high | Требования FR/NFR, «Паритет», сценарии UC |
| Математик-методист | Opus 5.5 / high | Мат. спецификации, допуски, самые трудные численные места |
| Автор независимого оракула | Sonnet 5.5 / high | Эталон на mpmath. **Отдельный агент**: пишет по учебникам, а не по спецификации ядра |
| Разработчик ядра | Sonnet 5.5 / high; рутина — medium | Расчёты |
| Разработчик интерфейса | Sonnet 5.5 / medium; диаграммы и редактор схемы — high | Окна, оболочка |
| Дизайнер UI/UX | Sonnet 5.5 / high + внешние нейросети | Концепции, макеты, дизайн-система |
| Инженер тестов | Sonnet 5.5 / medium | Тесты, фаззинг, разностные сравнения |
| DevOps | Sonnet 5.5 / medium | CI, установщики |
| Технический писатель | Sonnet 5.5 / medium | Руководства, справка, ЕСПД (скилл tech-docs-gost) |
| Исполнитель прогонов | Haiku 5.5 / low | Сборка, тесты, логи CI, сводки отличий |
| Поиск | Haiku 5.5 / low–medium (Explore) | Код, декомпилят, заметки |
| Ревьюер кода | Sonnet 5.5 / high | Уровни 1 и 2 |
| Ревьюер расчётов | Opus 5.5 / high | Уровень 1 |
| Ревьюер UX | Sonnet 5.5 / medium | Подэтапы с интерфейсом, по снимкам экрана |
| Ревьюер документов | Sonnet 5.5 / medium | Документы. Для ЕСПД дополнительно запускает `lint_doc.py` |
| Приёмка этапа | Opus 5.5 / high; ворота 5.10, 8.8, 9.5 — xhigh | Ворота этапов |

**Правила для субагентов:**
- Субагент не коммитит, не меняет ветку и ничего не публикует наружу.
- Один набор файлов правит один исполнитель. Параллельные исполнители работают в отдельных worktree.
- Сборки, прогоны со снимками экрана и сценарии с управлением окнами запускаются строго по одному.
- Задачу, проваленную дважды, оркестратор забирает себе.

## Уровни ревью
| Уровень | Что | Кто проверяет | Чем подтверждается серьёзное замечание |
|---|---|---|---|
| 1 | Ядро, расчёты, форматы файлов | Ревьюер кода (Sonnet high) + ревьюер расчётов (Opus high). Мат. спецификации дополнительно проверяет внешняя нейросеть (ВН) | Падающий тест или точный сценарий воспроизведения |
| 2 | Интерфейс и функции | Ревьюер кода (Sonnet high) + ревьюер UX (Sonnet medium) | Падающий тест или точный сценарий воспроизведения (шаги, снимок) |
| 3 | Документы, настройки, мелочи | Один ревьюер (Sonnet medium) | Цитата с файлом и строкой и источник, который показывает ошибку (план, заметка, код, ГОСТ) |

На каждом подэтапе с кодом работают проверки без LLM:
- линтеры;
- покрытие;
- мутационное тестирование;
- разностный фаззинг против оракулов;
- CI на трёх ОС.

Для документов — `python tools/check_links.py`, проверка ссылок.

**Серьёзность замечаний:**
- **блокирующее** — неверный расчёт, потеря данных, падение;
- **существенное** — расходится с требованием или планом;
- **незначительное**;
- **предложение**.

**Обозначения:**
- отчёт ревью — `reviews/RV-<подэтап>-<раунд>.md`;
- замечание — `R-<подэтап>-<n>`, со сквозной нумерацией по подэтапу через все раунды.

## Цикл подэтапа
1. **Готовность к работе (DoR).** Подэтап можно начинать, когда:
   - в `tracker.yaml` есть его пункт;
   - нет открытых развилок, которые его блокируют ([DECISIONS.md](DECISIONS.md));
   - с подэтапа 1.2 и дальше известны требования FR и строки «Паритета», если подэтап их касается;
   - есть мат. спецификация, если подэтап считает (с этапа 5; на этапах 1–2 спецификации только создаются);
   - сделан запрос к графу;
   - написано задание по [шаблону](templates/brief.md).
2. **Исполнение.**
   - `tracker.py mark <№> <неделя> "В работе"`.
   - Исполнитель делает работу вместе с тестами.
   - Исполнитель прогонов запускает весь набор тестов.
3. **Ревью.** Ревьюер — всегда другой агент со свежим контекстом.
   - Он получает дифф, требования, критерии, результаты прогонов и выдержку из графа.
   - Пишет отчёт по [шаблону](templates/review-report.md).
   - Блокирующее или существенное замечание принимается, только если подтверждено так, как указано в таблице уровней.
   - В колонке отчёта «Решение оркестратора» оркестратор отмечает каждое замечание: принято или отклонено, с причиной.
4. **Доработка** — если принято хотя бы одно блокирующее или существенное замечание.
   - Выполняются `tracker.py mark <№> <неделя> "Доработка"` и `tracker.py review …` по каждому принятому замечанию.
   - Замечания уходят тому же исполнителю (SendMessage, контекст сохраняется), затем идёт повторное ревью.
   - Исправленные замечания отмечаются командой `tracker.py review-status <ID> исправлено`.
   - Раундов не больше трёх. Дальше работу забирает оркестратор или решает пользователь.
5. **Приёмка (DoD).** Подэтап закрыт, когда:
   - оркестратор прочёл дифф и прогоны;
   - тесты зелёные на трёх ОС (с этапа 4);
   - строки «Паритета» этого подэтапа в состоянии «проверено» (с этапа 5);
   - сделан коммит;
   - выполнены `tracker.py log …` и `tracker.py mark <№> <неделя> Выполнено`;
   - CHANGELOG и документы обновлены;
   - граф обновлён: по коду — сразу, по документам — на воротах этапа;
   - незначительные замечания перенесены в [ISSUES.md](ISSUES.md) (`review-status <ID> отложено`).
6. **Ворота этапа.**
   - Приёмочный ревьюер (Opus) проверяет весь этап: требования, регресс, «Паритет», документы.
   - Он же сверяет роли (этот документ ↔ `tracker.yaml`) и обновляет граф по документам.
   - Пользователь получает демонстрацию (снимки или видео) и сводку.
   - На развилке работа встаёт на паузу. Если развилки нет, сразу начинается следующий этап (правило пользователя от 21.10.2026).

## Развилки
- Варианты, рекомендация, срок и действие по умолчанию записываются в [DECISIONS.md](DECISIONS.md) и на лист «Решения».
- Когда срок развилки наступает, оркестратор ставит её строке в графике работ статус «Ждёт решения».
- Решение пользователя записывается командой `tracker.py decision <Р-x> --answer "…"`, в журнал и в ADR, если оно архитектурное.
- Если ответа нет, действует колонка «Если ответа нет». Где там «Ждём ответа», без пользователя ничего не решается.

## Учёт
**Источник правды** — `tracker/tracker.yaml`. Excel собирается из него. Руками в Excel меняется только колонка «Комментарий»; её возвращает в yaml команда `sync`. Все команды запускает только оркестратор.

| Команда (`python tools/tracker.py …`) | Когда |
|---|---|
| `sync` | Перед любой правкой: забрать комментарии и решения пользователя из Excel |
| `build` | Собрать Excel. Остальные команды собирают его сами, если не указано `--no-build` |
| `add --id … --title … --parent …` | Новый пункт (подэтап, задача, ворота) |
| `mark <№> <неделя или дата> <статус>` | «В работе», «Доработка», «Выполнено», «Ждёт решения»; `-` снимает статус |
| `log --item … --what … --who …` | Запись истории (лист «История»), вместе с записью в `history/JOURNAL.md` |
| `review --item … --round … --severity … --text …` | Замечание ревью (лист «Ревью») |
| `review-status <ID> <статус>` | Открыто / исправлено / отложено / отклонено |
| `decision <Р-x> --answer …` | Решение пользователя по развилке |
| `parity …` | Строки листа «Паритет» и их состояние (команда появляется в доработке 0.5; до тех пор строки правятся в yaml) |

**Excel-график** повторяет образец пользователя:
- недельные колонки, первая неделя — 02.11.2026;
- шапка: «Сроки выполнения/месяцы» → год → месяц → даты недели → номер недели;
- строки этапов жирные на сером фоне;
- праздники и сессия затенены.

Статусы и цвета:

| Статус | Цвет |
|---|---|
| «План» | фиолетовый |
| «Выполнено» | тёмно-зелёный |
| «Доработка» | жёлтый |
| «В работе» | синий |
| «Ждёт решения» | красный |

Листы: «График», «Сроки», «История», «Ревью», «Решения», «Паритет», «Легенда».

Если файл открыт в Excel (рядом лежит `~$…`) или занят синхронизацией OneDrive, сборка ничего не пишет и завершается с кодом 2. Тогда нужно попросить пользователя закрыть файл.

## Внешние нейросети
1. Когда подэтап из ROADMAP §6 доходит до точки ВН, оркестратор готовит `external/ВН-xx.md` по [шаблону](templates/external-request.md). Запрос самодостаточный: все данные вставлены в текст.
2. Оркестратор говорит пользователю, что запрос готов. В графике работ подэтап получает статус «Ждёт решения».
3. Пользователь отправляет запрос и вставляет ответ в раздел «Ответ» (или кладёт файлы в `external/ВН-xx/`).
4. Оркестратор разбирает ответ:
   - замечания из ответа становятся замечаниями ревью (`tracker.py review`, «Кто нашёл» — ВН-xx);
   - в файле запроса записывается, что принято и что нет;
   - делается запись в журнале.

## Граф знаний
- **Два графа.** `..\graphify-out` — Delphi и разбор оригинала. `graphify-out` в этом репозитории — новый продукт.
- **Перед подэтапом.** `/graphify query "<тема>"` (или `path`, `explain`). Выдержка из ответа идёт в задание.
- **После подэтапа с кодом.** `/graphify <путь> --update`. Код обновляется без LLM.
- **Документы.** Файлы `.md` и `.svelte` разбирает LLM, поэтому граф по документам обновляется только на воротах этапа.
- **Полезные ответы.** Сохраняются командой `python -m graphify save-result …`.
- **Связи** «требование ↔ спецификация ↔ модуль ↔ тест» держатся на ссылках в документах — только так они видны в графе.

## Документация
| Документ | Стандарт и образец |
|---|---|
| Требования `requirements/SRS.md` | ISO/IEC/IEEE 29148, шаблон [templates/requirement.md](templates/requirement.md) |
| Архитектура `architecture/` | arc42 и диаграммы C4 |
| Решения `adr/NNNN-*.md` | Формат M. Nygard, шаблон [templates/adr.md](templates/adr.md) |
| Математика `math/` | По каждой формуле: источник, допуск, способ проверки |
| Испытания `testing/` | Облегчённый ISO/IEC/IEEE 29119-3, шаблон [templates/test-case.md](templates/test-case.md) |
| Изменения [../CHANGELOG.md](../CHANGELOG.md) | Keep a Changelog, версии по SemVer |
| ЕСПД `espd/` | ГОСТ 19.201, 19.402, 19.505, 19.301 (+ 19.401). Оформление — скилл tech-docs-gost. Нормоконтроль — его `scripts/lint_doc.py` (проверяет `.docx`) |
| Руководство пользователя `user/` | Пишется к выпуску вместе со справкой |

**Стиль текста:**
- русский язык, короткие предложения, безличная форма («оркестратор готовит», «пользователь решает»);
- термины — по [глоссарию](glossary.md) и методичке кафедры.

## Публичный репозиторий
- **Не кладём:**
  - exe и `.HLP` оригинала;
  - декомпилят Ghidra;
  - снимки окон оригинала;
  - дословный текст его справки (Р-6).

  Всё это хранится вне `tau3-ng` или в `local/` (папка в `.gitignore`). Список запрещённых масок — в [CONTRIBUTING.md](../CONTRIBUTING.md). Проверка перед коммитом появится в подэтапе 4.3.
- **Публикация на GitHub** (push, создание репозитория, релизы) — только с подтверждения пользователя.
- **Коммиты** — в формате Conventional Commits, см. [CONTRIBUTING.md](../CONTRIBUTING.md).
