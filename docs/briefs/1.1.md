# Задание субагентам: 1.1 Функциональные требования и «Паритет»

Подэтап делят три исполнителя: А, Б и В. Общие разделы — для всех. Раздел «Исполнитель …» — только для своего.

## Роль, модель, effort
Аналитик требований — Sonnet 5.5 / high (каждый из трёх исполнителей).

## Цель
Записать функциональные требования (FR) ко всему, что умеют CONTROL 1.1 и CONTROL 2, и строки листа «Паритет» на уровне поведения. По ним этап 6 переносит функции, а ворота 6.9 проверяют, что ничего не потеряно.

- **Внешние нейросети.** Нет.
- **Требования.** NFR — в `docs/requirements/SRS.md`, раздел 4. На них ссылаемся, их не повторяем.
- **План.** `docs/ROADMAP.md`:

## Что сделать (общее для всех)
1. Прочитать свои заметки и код. Выписать каждое поведение, которое видит пользователь: пункты меню и окна, поля и их пределы, клавиши, мышь, сообщения, файлы, что считается и что рисуется. Для CONTROL 2 — каждый пункт с отметкой ✅ или ◐ из `CONTROL_src/ROADMAP.md`, который относится к вашим областям.
2. **Записать FR** по шаблону `requirement.md`:
   - Одна FR — одно поведение, которое проверяется одним тестом или одним сценарием. Мелочи одного окна, которые проверяются вместе, можно объединить.
   - **«Требование»** описывает поведение, а не устройство Delphi: без VCL, адресов, имён форм. Если механизм оригинала устарел (WinHelp, BMP, CP866, вид диалогов Delphi 7), FR сохраняет цель, а механизм указывается в «Обосновании».
   - **«Источник»:** `1.1` или `К2`, ссылка на Delphi `<файл.pas>:<строка>` по метке `v2-delphi-final` и заметка `<notes/файл.md> §…`. Поведение, которое есть и в 1.1, и в CONTROL 2, получает источник `1.1`.
   - **«Проверка»:** вид теста и эталон. Эталоны и допуски ещё не созданы, поэтому пишем так: «эталон: оракул Delphi (1.4)» и/или «mpmath (1.5)», «допуск: по `docs/testing/tolerances.md` (1.3)».
   - **«Паритет»:** ID строки `P-<область>-<NNN>`.
   - **«Подэтап»:** кто реализует. Расчёт — подэтапы 5.x, окно или поведение интерфейса — 6.x. Если нужны оба, пишем оба.
   - Номера `FR-<область>-<NNN>` идут по порядку с 001 в каждой своей области.
3. **Строки «Паритета».** В конце своего файла — таблица со столбцами строго такими, без лишних:

   `| ID | Область | Поведение | Источник | Delphi | FR | Подэтап |`

   - Источник: `1.1` или `К2` (буква К кириллицей).
   - Каждая FR — минимум в одной строке, каждая строка ссылается на свою FR.
   - «Поведение» — до 120 знаков, без символа `|`.
4. **Причуды и ошибки оригинала.** Если поведение оригинала похоже на ошибку или причуду, FR описывает правильное поведение. Причуда пишется в «Обоснование» с пометкой «причуда → 1.7».
5. **Открытые вопросы.** Раздел «Открытые вопросы» из своих заметок, плюс свои вопросы, возникшие при работе. Формат: `ОВ-<буква исполнителя>-<n>: вопрос — где — на что влияет`.
6. **Передать другим.** Если нашлось поведение из чужой области, FR на него не пишем. Записываем его в раздел «Передать другим»: что, где, кому (А, Б или В).

**Дополнительно для В — регресс по аудиту** (`audit.md`), файл `docs/testing/cases/audit-regress.md`:
- по шаблону `test-case.md`, номера `TC-AUD-<NNN>`, в названии — ID из аудита (A0…A10, B1…B7, C…, D…);
- **A0–A10 и B1–B7** — тест-кейс на каждую ошибку, у которой есть наблюдаемое поведение: шаги, исходные данные, ожидаемое правильное поведение;
- **C и D** — тест там, где эффект наблюдаем. У остальных — строка таблицы «неприменимо» с причиной (качество Delphi-кода, инструменты);
- в «Проверяет» — FR из любой области. Если подходящей FR ещё нет, пишем «FR — у исполнителя А/Б» и область.

**Пункты CONTROL 2 с отметкой «— не сделано»** (2.5, 2.6, 3.2, 4.7, 5.2) в FR не входят. Их перечисляем одной строкой в конце файла — это кандидаты для этапа 7.

## Файлы
- **Можно менять:** только файлы из своей колонки «Пишет файлы». Папки создать, если их нет.
- **Нельзя трогать:** `SRS.md`, `tracker.yaml` и Excel, файлы других исполнителей, всё вне `TAY-4`. Сборку графа и учёт ведёт оркестратор.

## Ловушки
- **Публичный репозиторий.** Нельзя переносить: дословный текст справки оригинала и CONTROL 2, декомпилят, адреса вида `@004A…`, снимки окон. Названия пунктов меню, окон и полей можно — это интерфейс, а не текст справки. Тексты сообщений об ошибках пишем пересказом. Дословный текст сообщения допустим, если он не длиннее 10 слов: по нему тест узнаёт сообщение.
- **Заметки и код.** Заметки иногда расходятся с кодом. Верна поправка из `notes/README.md`; если её нет — код копии. Расхождение записываем в «Открытые вопросы».
- **«Попиксельно»** в `CONTROL_src/README.md` говорит о соответствии копии оригиналу. Для ТАУ-4 это не требование: новый интерфейс другой, переносится поведение.
- **Термины.** Буквы v, x, h и «Wраз» — по глоссарию.

## Сведение (исполнитель Г, после А, Б и В)
Роль — аналитик требований, Sonnet 5.5 / high. Один агент правит все четыре файла: `docs/requirements/fr/scheme-input.md`, `analysis.md`, `output-shell.md` и `docs/testing/cases/audit-regress.md`. Остальные правила задания действуют.

1. **«Передать другим».** Разобрать каждую запись трёх файлов.
   - Если получатель уже покрыл поведение, дописать в запись «→ FR-…».
   - Если не покрыл, добавить FR в файл и область получателя (следующий свободный номер) и строку «Паритета», затем дописать «→ FR-…».
   - Раздел переименовать в «Передано другим (сведено)».
2. **Дубли.** Если одно поведение описано в двух FR, оставить FR в области-владельце по таблице «Распределение». У второй FR:
   - текст заменить на «Снято при сведении: дублирует FR-…»;
   - номер не переиспользовать;
   - её строку «Паритета» удалить, а ссылки на неё в других файлах заменить.
   
   Если FR дополняют друг друга (например, окно ввода у А и расчёт по нему у Б), это не дубль. Тогда добавить взаимные ссылки в «Обоснование».
3. **Заглушки в `audit-regress.md`.** Заменить «FR — у исполнителя …» на настоящие ID.
4. **Заявлено в `CONTROL_src/ROADMAP.md`, но нет в коде.**
   - **Правило.** «Паритет» — это только поведение, которое есть в коде 1.1 или CONTROL 2.
   - **Что сделать с такими FR.** Оставить их, но:
     - «Источник» → `новое (в ROADMAP CONTROL 2 отмечено ✅, в коде нет)`;
     - поле «Паритет» → `—`;
     - их строки из таблицы «Паритета» удалить.
   - **Сводный список.** Пункт ROADMAP CONTROL 2, чего нет в коде, какие FR — в отчёт. Его оркестратор перенесёт в SRS и в исправление `CONTROL_src/ROADMAP.md`.
5. **Столбец «Область»** во всех таблицах «Паритета» — код области (`SCH`, `RTH`, `GRF` и т. д.), а не слово.
6. **Проверка.** Все три таблицы вместе:
   - разбираются (7 столбцов, источник `1.1` или `К2`);
   - ID уникальны во всех трёх файлах;
   - каждая FR с полем «Паритет» ≠ `—` есть в таблице, и наоборот;
   - каждая ссылка `FR-…` во всех четырёх файлах ведёт на существующую FR;
   - `check_links.py` — 0 битых ссылок.

**Отчёт Г:**
- сколько записей «Передать» закрыто ссылкой и сколько добавлено FR;
- сколько FR снято как дубли (пары);
- сводный список из п. 4;
- итог: FR по областям, строк «Паритета»;
- что не удалось свести — вопросом.
